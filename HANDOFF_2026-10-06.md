## 5. The text-rendering finding (start here)

On the title, Xenia draws "Press START" as **one quad list of 40 vertices** (10 glyphs). It uses:

- **VS** ucode `43E408D6BB8294C9`:
  - position f32×3, colour 8888 and UV f32×2, stride 24, read from **vertex fetch constant 95**;
  - outputs `uv + c53` and `colour × c40`.
- **PS** `9F3AB9282CC3CCCD`: BGRA texture fetch × 2 × colour, with global alpha `c39.w × c44.x`.
- A **512×512 BC3 font atlas**.

**In our runtime that sprite VS is never loaded or translated.** Our command stream between D3D's clear and that point contains no shader load at all. Every draw packet we receive is recorded (`[DRAWIN]` shows `rec=1` for all of them).

So **the game itself doesn't submit the text draw**: a game-state or logic difference, not a renderer bug. We never confirmed why. Candidates:
- a timer-driven UI fade that stays at 0;
- the attract movie: Xenia plays `D:\MOVIES\NTSC\DEMOINTRO.WMV` and opens `.SUB`; we open the WMV 6× and never show or open `.SUB`;
- input or profile state.

**Why this matters for your task:** the menu items, "Select (A)" and in-level hints are almost certainly drawn by the same font path (same sprite VS/PS, same atlas). Two cases:
- **Our build shows the menu with no text:** expect the same root cause, and find out why the game never binds the sprite shader.
- **The text draws but looks wrong** (missing glyphs, wrong colour, wrong placement): it's a renderer problem, and the tools in §6 will find the failing draw.

Boot-screen text **does** render. It uses a different sprite VS at guest `0x8102A040` (306 dwords) with PS `0x8102B040`. So some text paths work, which helps narrow the menu one down.

Suggested first steps:
1. Run our build, press Enter at the title, and capture a few frames with RenderDoc. Also log draws (§6, `imlog_now` / `[DRAWIN]`).
2. Capture **Xenia** on the same screen (§7) and diff the draw lists: vertex counts, topology, shaders, textures.
3. If Xenia has font draws (sprite VS + BC3 atlas) that we never receive, trace upward in game code: find the D3D call that binds the sprite VS and see why it isn't reached. Useful anchors:
   - D3D's vertex-shader bind/patch path is `sub_822B6610` → `sub_822B64D0` (slot check) → `sub_822B59D8` (memcpy of the patched variant).
   - Hooking `sub_822B64D0` to log the shader-object pointer per bind shows which shaders the game binds each frame. There's already a diagnostics hook there: `lswtcs_slotchk`, a recomp edit in `ppc_recomp.342.cpp`.
4. Check menu input separately: with the text missing, the highlight may still move and select. Pressing Down and then A should still change state, which tells you whether input parsing works.

## 7. Xenia as ground truth

`xenia/xenia_canary.exe` is a release build: GPU frame traces (F4) are **compiled out**. What works:

**RenderDoc capture of Xenia:**

```
"/c/Program Files/RenderDoc/renderdoccmd.exe" capture -d "C:\...\xenia" -c "C:\...\xenia\rdcap\xen" \
  "C:\...\xenia\xenia_canary.exe" --log_level=1 --trace_functions=false --trace_function_coverage=false \
  --trace_function_data=false --trace_function_references=false "C:\...\Convert 360\LSWTCS\Default.xex"
```

Then send F12 from PowerShell:

```
$ws = New-Object -ComObject WScript.Shell
[void]$ws.AppActivate(<pid>)
[System.Windows.Forms.SendKeys]::SendWait("{F12}")
```

The title appears about 10 s after launch. To reach the start menu, send `{ENTER}` first (or Xenia's mapped Start key), wait, then send F12. Existing title captures: `xenia/rdcap/xen_frame340.rdc`, `xen_frame632.rdc`.

- **Always** override `log_level` and `trace_functions*` on the command line. The config file has debug logging plus function tracing on, which makes Xenia crawl. Don't edit the user's config.
- `--dump_shaders=<dir>` writes Xenia's ucode and disassembly.
  - Xenia's hashes **don't** match ours, so compare by disassembly text with comments and whitespace stripped (the Python one-off used is in this session's log).
  - Xenia's disassembler names vertex fetch constants **reversed**: "vfN" means constant 95−N.
- Xenia's config has `gpu_allow_invalid_fetch_constants = true`. Draws that read a texture constant as vertex data run in Xenia but are skipped by us, for example D3D's leftover 4-vertex fade quad. That's harmless, but don't mistake it for a bug.

## 8. Known caveats

- **RenderDoc offline replay** can show a clean frame when the live one is broken. Trust the live thumbnail, `resdump_now` and `[XDLOG]`.
- **Post-VS data** must be read through `m.indexResourceId`: it's a unique-vertex buffer.
- **RenderDoc's shader debugger** mis-executes Xenia's `switch` (it falls through cases). Don't trust its traces. The call is `DebugVertex(row, inst, rawIndex, view)`.
- **The shared-memory residency map never evicts.** Watch memory if levels churn.
- **Other "GPU caught up" shortcuts remain:** `lswtcs_ad6a0_phase`, `lswtcs_ad778_get`, the VdSwap RPTR writeback. They may cause more D3D resource-reuse bugs like the shadow one. If something looks like the wrong version of a buffer or shader, suspect these.
