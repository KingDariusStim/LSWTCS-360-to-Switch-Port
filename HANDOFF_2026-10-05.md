## 1. Working rules (from the user, mandatory)

- **Launch exactly ONE game instance.** Check `tasklist | grep -i lswtcs` before launching. A freshly linked exe takes about 15 s to show up in tasklist; don't double-launch.

- RenderDoc stays on for user sessions (don't pass `LSWTCS_NORDOC`). The user takes captures with the RenderDoc key and they land in `LSWTCSRuntime/build/rdoc/cap_frame<N>.rdc`.
- Back up before risky changes: `./backup.sh <label>`. Note it does **not** copy `LSWTCSRuntime/xenos_dxbc/`.
- Write patch scripts to files with the Write tool (Python, `patch(path, [(old, new, count)])` pattern) and run them. Don't patch through heredocs, which mangle `\n`. `gpu_xedraw.inc`, `gpu_d3d12.cpp` and the recomp `.cpp` files are CRLF, so the patch helper normalises line endings. Templates are in the session scratchpad (`patch_*.py`); copy the `patch()` helper.
- Never fake old CPU speed; timing follows real time.
- At a real roadblock the user prefers the three-agent pattern (one of them a skeptic).

## 2. How to run

```
cd <project root>
./run.sh build
EXTRA="LSWTCS_PRISTINE=1 LSWTCS_FPS_CAP=60 LSWTCS_HEAPBYPASS=0 LSWTCS_GAMEROOT=X:/none/ LSWTCS_WAITREG=0" ./run.sh run 3600   # run in background
```

- **`LSWTCS_WAITREG=0` is required.** With the GPU-side WAIT_REG_MEM emulation on (the current default), the game freezes shortly after reaching the hub: frames keep presenting, but the game never submits GPU work again and the tile worker `sub_822D2AB0` is woken without an interrupt. Consider making `0` the default in `kernel_stubs.cpp` (search `LSWTCS_WAITREG`).
- Logs:
  - `LSWTCSRuntime/build/run_out.txt` (stdout: XDLOG / FSIG / BLUE / SKIPDT / STALE);
  - `LSWTCSRuntime/build/trace.log` (dbg_ram: VdSwap / DRAWSTAT / WAITREG / IBINT ...).
- Live triggers: create an empty file in `LSWTCSRuntime/build/` and it's consumed within about 30 frames.
  - `xdlog_now`: one frame of replay log (every draw: mode/pitch/viewport/zctl/blend, and each texture binding with fetch index, base, format, size, and RESOLVED vs guest).
  - `resdump_now`: dumps the resolve targets.
  - `skipdt`: toggles skipping the **shadow-mask pass** (see §4). Logs `[SKIPDT]`.

## 4. What the floor glitch / shadow actually is (evidence)

User description:
- floor textures flicker between correct and "stretched from their origin point";
- some character positions and orientations never glitch;
- it almost always glitches while the character moves, jumps, or the idle animation turns the head;
- the streaks seem anchored to world coordinates.

Shadow description:
- a dark wedge with a constant offset and direction from the character's head;
- player 1's wrong shadow follows them around, and the NPC (player 2) doesn't start following until it's inside that shadow;
- player 2's glitch is a straight line that follows player 1.

**The hub frame pipeline**, from `xdlog_good.txt` (`LSWTCSRuntime/build/xdlog_good.txt`, a full XDLOG of one frame):
1. Tiles 0/1/2: world draws into a 2× MSAA 1280-pitch EDRAM target. Each tile resolves colour 0 → `0x0A909000` (k_8), colour 1 → `0x0AC4D000` (k_8) and depth → `0x0AA95000` (fmt 4), at base, base+288 rows and base+576 rows.
2. Shadow map: depth-only (mode 5) draws into an 800-pitch target. Record #820 resolves depth into `0x0AF9D000` (768×1344).
3. **Shadow-mask pass** (#822): a half-res 640×704 target, a 2,640-index grid draw, 8 textures:
   - fetch2 = `0x0AC4D000` (k_8 colour 1);
   - fetch0 = `0x0AA95000` (scene depth, fmt 4, swizzle XXXX);
   - fetch1 = `0x0AF9D000` (shadow map, fmt 4, **clamp-to-border, border = white**);
   - fetch3 = `0x0B4F1002`.

   It resolves to `0x0B415000`.
4. Downsample chain into the mask's packed mip levels: `0x0B499000` 320×352, `0x0B4D9000` 160×176, `0x0B4E9000` 80×88.
5. **Final composite** (#842): a full-res 2,640-grid draw. It samples:
   - fetch5 = `0x0B415000` **with mips** (`sample_l` with computed LOD = soft shadows / penumbra);
   - fetch4 = `0x0A909000`;
   - fetch2 = `0x0AC4D000`;
   - fetch0 = depth.

   It then resolves to the frontbuffer.

**Observations:**
- RenderDoc offline replay of `cap_frame2562` shows the floor draw (eid 8399, 1,479 indices, 10 SRVs) writing a **clean** floor into the scene RT. **Caveat from the user:** captures may not land on a glitched frame, so this doesn't prove the floor draw is always clean.
- Offline replay of the shadow mask (eid 17882 in `cap_frame2562`) shows mask data only inside a trapezoid, the shadow map's coverage area projected onto the scene. That boundary is the likely "wedge".
- Skipping the mask pass (`skipdt`) froze the shadows on screen (stale mask). The streaks stayed, but that test is **inconclusive**, because the stale mask still held the streaks. The right test is to force the mask to white (lit) instead of skipping it.
- The two depth textures are sampled as **TextureFormat 4 (k_5_6_5), swizzle XXXX**. We store depth resolves as `R32_FLOAT` and sample the float directly. The mask shader (DXBC in `build/rdoc/fe/fetch.txt`) treats the `.x` sample as full-precision depth (`z = -d*c + c'`, then `rcp`), so float depth seems semantically right. But real hardware returns k_5_6_5 decoded from raw D24S8 bits. **This mismatch is unresolved**; see §6, item 2.
- The 192-index draws that also sample depth are the six door-number signs. They're irrelevant.

## 5. Ruled out this session (with evidence)

| Hypothesis | How it was tested | Result |
|---|---|---|
| Vertex data changing between tile passes | `LSWTCS_VDIV` hashed vertex bytes per (VS, index count, ranges) across tiles | 40k repeats, 0 diverged |
| Exploded or NaN texcoords in world draws | `rd_attrs.py` over every VS output slot | only HUD/post draws are out of range |
| Mipmap decoding (packed mips) | `LSWTCS_GPUDRAW_NOMIPS=1` | glitch unchanged |
| Stencil shadow volumes | `[STENCILDRAW]` log of every stencil-enabled draw | only 3-vertex stencil-write clears exist |
| Depth clip | `DepthClipEnable` from clip_disable | no change |
| Sampler border colour | the §3 fix | shadows unchanged |
| Z-fighting between floor layers | XDLOG: the floor mesh is drawn once per tile, with no second layer | not the cause |
| "Blue patch" broken frames (cap 6431/6501: squashed image, black bar, blue panels) | FSIG showed identical frame structure; BLUECATCH over about 3,000 live frames caught nothing; the user saw no blue live | **almost certainly a RenderDoc-capture artifact, ignore** |

## 6. Recommended next steps (in order)

1. **Force the shadow mask white.** Turn the `skipdt` toggle into "replace": instead of skipping the pass, clear the mask target to white and skip its draw, or make the composite's fetch5 bind a white texture. If the floor streaks **and** the head wedge both vanish live, the glitch is in the shadow pipeline. Ask the user to toggle on a glitched tile.
2. **Get ground truth for sampling depth resolves as k_5_6_5.** Find out what Xenia does for this game. Ideally run Xenia canary on the same disc (there's an `xdump.ps1` memory dump tool; see memory `xenia_memory_dump.md`) and check whether the hub floor and shadows look right there. If they do, port Xenia's semantics. In Xenia, a depth resolve writes raw D24S8 (`DepthRenderTargetToTextureFormat`, `draw_util.cc` ~line 1105), and a later fetch as k_5_6_5 decodes those bits. Note the related open question of why `LSWTCS_K8RGBA` (keeping k_8 resolves as RGBA) is needed at all. Both hint that the game reinterprets resolved memory bit-exactly. The full fix is to write resolves to guest memory bit-exactly (Xenia's resolve compute shaders) and decode textures from it.
3. **Check the shadow map itself.** Look at the mode-5 draws into the 800-pitch target and resolve #820:
   - is it cleared to far depth each frame (the game clears with 3-vertex ALWAYS/write draws, `zctl 0x8777`)?
   - is the 768×1344 resolve rectangle and size right?
   - does the per-tile window offset or scissor apply to it?

   A shadow map that keeps stale depth from previous frames would explain the trails that move with the character.
4. Only after that, look at the floor shader itself (`cap_frame2562`, eid 8399; 7 DXT1 1024² textures, fetch3–6 with packed mips).

Other open items, lower priority:
- red translucent HUD "shard" quads drifting around the viewport;
- pause-menu rendering quality;
- 3-core (Switch Mariko) multithreaded scheduler (deferred; see memory `switch_multithreading_constraint.md`).

## 7. Tools written this session (`LSWTCSRuntime/build/rdoc/`)

Run headless as:

```
RD_CAP=<abs .rdc> RD_OUT=<dir> timeout 600 "/c/Program Files/RenderDoc/qrenderdoc.exe" --python <script>
```

| Script | Purpose / extra env |
|---|---|

| `rd_attrs.py` | Per-draw range of every VS output slot |
| `rd_bbox.py` | Screen bbox of draws with `RD_IDX` indices (position is at VS-out offset 0) |
| `rd_psdis.py` | PS + VS DXBC disassembly of the first draw with `RD_IDX` indices |
| `rd_fetch.py` | Fetch-constant dump (6 dwords per fetch, decoded format) + PS DXBC; `RD_IDX`, `RD_SRV` (min SRVs), `RD_VPW` (viewport width filter) |
| `rd_rtsave.py` | Saves RTs as PNG after `RD_EID` |
| `rd_pixwalk.py` | Reports every draw that changes RT0 pixel(s); `RD_PX="x,y;x,y"`, `RD_MAXEID` |
| `rd_struct.py` | Run-length frame structure |
| `rd_srvsize.py` | SRV sizes of the last `RD_LAST` draws |

Thumbnails: `"/c/Program Files/RenderDoc/renderdoccmd.exe" thumb X.rdc -o X.png -f png`. A PowerShell `System.Drawing` contact-sheet snippet was used for `rdoc/series_sheet.png`. There's no PIL or numpy.

⚠️ **RenderDoc offline replay does not reproduce our resolve/composite chain faithfully**: resolve targets come out white, and the final image differs from the live one. Draw lists, shaders, fetch constants and VS output are trustworthy. For pixels, prefer in-process dumps (`resdump_now`, `xdlog_now`, `LSWTCS_SHOTS=N`).

Decoding fetch constants (`xenos.h` ~line 1240, `xe_gpu_texture_fetch_t`):
- dword0: `pitch = (d0>>22)&0x1FF` (×32), `tiled = d0>>31`, `clamp_x/y/z` at bits 10/13/16;
- dword1: `format = d1&0x3F`, `base = d1&0xFFFFF000`;
- dword2: `w = (d2&0x1FFF)+1`, `h = ((d2>>13)&0x1FFF)+1`;
- dword3: swizzle at bits 1–12, filters at 19+;
- dword4: `mip_min = (d4>>2)&0xF`, `mip_max = (d4>>6)&0xF`;
- dword5: `border_color = d5&3`, `packed_mips` = bit 11, `mip_address = d5&0xFFFFF000`.
